## Published task identity without a self-referential hash

is unchanged. Let P be the later commit publishing the immutable HY3 task and
its queue digest. P contains the task; E need not contain it. C is an ancestor
of E, and E is an ancestor of P. The worker executes at the task base E (or its
explicit later approved base), not at P. All three must be existing full Git
commits; record their precise values. Do not demand that a task exist in E.

At creation, the production CLI obtains the assigned task from the runner's
.runtime/task.json. It resolves and records a published Git snapshot P whose
ops/tasks/<id>.json matches that task and whose queue has that exact canonical
task SHA256, owner=hy3, kind=commands, ready state and branch/attempt. Git main
may have advanced since publication; a later snapshot carrying the unchanged
ready task is sufficient. This is evidence binding, not permission to fetch,
merge, change branches or accept an arbitrary caller-supplied task. Validate
P against the fetched origin/main ancestry. Task digest uses the runner's
json.dumps(task, sort_keys=True, separators=(',', ':')).encode() SHA256 rule.
A task reference can be read from that explicit Git object, without trusting
.runtime/task.json alone. No current-HEAD equality is required for later replay.

acceptance using the queue and chief acceptance records at that base: each
record must identify the accepted exact reviewed commit and required positive
