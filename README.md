## 2. A 题究竟要做什么

SafeInvest 是一家虚构金融科技公司。客户填写问卷，系统在保守型、均衡型、成长型中推荐组合，也可以请求人工审核。资产仅包括股票、政府债券和短期票据代理资产。

我们需要建立可执行的决策流程：

```text
客户问卷 → 客户适配 → 组合配置 → 每年检查
         → 保持 / 再平衡 / 改变目标 / 人工审核
         → 用独立市场情景验证效果与风险
```

### 2.1 三项主要任务

| 任务 | 需要回答的问题 |
|---|---|
| 客户适配 | 三种组合怎样定义？怎样结合期限、损失容忍度、流动性需求推荐？哪些客户需要人工审核？ |
| 自动化组合策略 | 均衡型什么时候交易或更新目标？预期改善能否覆盖费用？与规定基准相比是否增加价值？ |
| 可靠性和保障 | 结论对假设或交易费率是否敏感？何时暂停自动决策？等待人工审核时怎么办？ |

### 2.2 五位客户

| 客户 | 期限 | 暂时性购买力损失容忍度 | 流动性需求 |
|---|---:|---:|---|
| A | 5 年 | 10% | 高 |
| B | 15 年 | 25% | 中 |
| C | 30 年 | 40% | 低 |
| D | 25 年 | 15% | 中 |
| E | 6 年 | 35% | 高 |

客户的损失容忍度是问卷回答，不是我们能够保证的损失上限。客户 D、E 的信息存在需要权衡的因素，不能只凭期限或单个风险分数机械分配。

### 2.3 数据与基准

- 数据共 180 个独立合成情景，每个情景 30 年，共 5,400 行。
- 字段包括情景编号、年度、股票收益、债券收益、票据代理收益和通胀率。
- 收益和通胀均为小数；这些数据不是真实历史事件，也不是预测。
- 指定基准：股票、债券、票据目标各为三分之一，每年恢复比例并计入费用。
- 题目要求对每种策略报告增长中位数、严重损失中位数、增长第 10 百分位、严重损失第 90 百分位；另报告交易占比并分析严重亏损案例。

更完整的中文翻译、字段解释及初步建模思路见[题意说明](docs/PROBLEM_A_ZH.md)。最终以原始英文赛题为准。

## 3. 为什么按这三类职责分工

三个 AI 都独立完成整道题，会产生重复工作和不同口径。我们选择让主要实现、独立核查、报告写作形成明确交接。

| 角色 | 负责 | 主要产出 | 文件边界 |
|---|---|---|---|
| 主 AI | 模型、主程序、实验、问题修复、最终整合 | 配置、代码、逐期账本、结果、图表 | 主代码及实验目录 |
| 核查 AI | 原题对照、独立复算、代码与结果审查、修复复核 | 核查代码、问题清单、复核结论 | 主要维护 `audit/`，对主实现只读 |
| 报告 AI | 结构、假设、符号、解释、文献、英文报告 | 报告草稿及最终文档 | 主要维护 `report/` |

具体约定：

1. 主 AI 负责形成并执行方案，核查 AI 不代替其编写主模型。
2. 核查发现问题后，由原负责人修复，核查 AI 再检查新版本。
3. 报告 AI 不编造数值、不把候选方案写成已证实结论。
4. 关键假设由主 AI 记录，核查 AI 可以提出问题和建议；变更必须同步到代码与报告。
5. AI 可以承担代码、计算、图表和报告整理。队员负责理解关键假设、核对成员信息及最终提交。

## 4. 不同电脑如何通过 GitHub 协作

### 4.1 GitHub 共享什么

每台电脑保留自己的本地副本。通过 GitHub 上传和获取文件，大家使用相同版本进行实现、核查和写作。

**本地路径和聊天内容不会因为使用同一个仓库就自动共享。** 例如，一台电脑上的 `E:\2026_MCM` 只是该电脑的路径。另一个 AI 应读取仓库中的文件，而不是尝试访问这条本地路径。

### 4.2 账号与工具准备

1. 仓库拥有者在 `Settings → Collaborators → Add people` 邀请队友的 GitHub 账号。
2. 队友接受邀请，并在自己的电脑或 AI 工具中完成相应 GitHub 授权。
3. AI 有文件与 Git 操作能力时可以执行克隆和推送；只有对话能力时，由队友下载或上传文件。
4. GitHub 连接权限取决于各自账号和安装授权。本聊天能访问仓库，不代表另一个聊天已经获得权限。

授权方式参考 [GitHub 官方说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository)。

### 4.3 基本工作方式

以下为使用 Git 的示例，工作目录由各台电脑自行选择：

```bash
git clone https://github.com/luckytoday789/2026_MCM.git
cd 2026_MCM
git status
git branch -a
```

建议使用这些分支：

| 分支 | 用途 |
|---|---|
| `main` | 汇总确认的代码、结果和报告 |
| `model` | 主模型与实验开发 |
| `audit` | 独立核查程序及记录 |
| `report` | 英文报告和排版 |

不存在的分支由对应负责人从明确的已有提交创建；分支已存在时获取现有分支，不覆盖他人的提交。各自提交后用 Pull Request 交接，由主负责人协调合并。不要强制推送改写共享历史。

每个聊天需要接到明确的任务或交接消息后继续工作。**不要假定某个 AI 会因为仓库发生变更，就自动开始持续监控或自动收到其他聊天的对话。**

## 5. 仓库目录与文件归属

建议结构如下。已有合理结构可以沿用，不要求为目录形式反复迁移文件。

```text
2026_MCM/
├── README.md                  本协作流程
├── docs/
│   ├── PROBLEM_A_ZH.md         中文题意及候选路线
│   └── MODEL_SPEC.md           主 AI 编写的模型约定
├── data/                      原题、原始数据及来源说明
├── src/                       主程序
├── configs/                   参数、策略及冻结配置
├── tests/                     主程序必要测试
├── results/
│   ├── development/           开发及内部验证结果
│   └── final/                 冻结后的最终评估结果
├── audit/                     独立核查说明、程序及记录
└── report/                    报告源文件、图表及最终版本
```

这是建议结构，尚未创建的目录不代表已完成相应工作。首次文档提交只提供协作和题意材料，原题、数据、代码和结果由相应负责人补充。

主 AI 的 `MODEL_SPEC.md` 至少说明：费用支付约定、交易时序、增长与风险指标、客户适配规则、策略参数、信息边界、人工审核动作和评估期限。核查与报告均以该具体版本为对象。

原始数据保持不变；如另存处理后数据，需记录变换方式和来源。数据与题目来源及许可说明不得在整理文件时丢失。

## 6. 完整实施流程

### 阶段一：准备输入和基准

**主 AI：**

- 获取原始 PDF 与 CSV，检查字段、情景、年度、缺失和重复记录。
- 固定开发与最终测试边界，建立模型约定文档。
- 实现统一财富账本与规定的等权年度再平衡基准。
- 先跑开发集，输出至少一个情景的完整账本和逐情景指标。

**核查 AI：**对照原题，准备独立手算例子，核查基准实现。

**报告 AI：**阅读原题，建立任务覆盖表、报告大纲、符号表和假设列表，查证必要参考文献。

**阶段交付：**代码入口、依赖、费用约定、基准结果、逐期账本及 commit SHA。

### 阶段二：先确认计算基础正确

核查 AI 检查初始配置费用、单向收费、资金守恒、收益和通胀时序、基准比例及无未来信息使用。必要时在 `audit/` 另写小规模独立程序，而不是只调用主程序复算。

发现问题后，主 AI 修复并提供新提交。核查 AI 记录复核证据；“运行无报错”不等于“计算正确”。

### 阶段三：设计客户适配和组合管理

主 AI 使用前 120 个情景开发方案，必要时在其中按情景划分内部训练与验证部分。

- 选择少量可解释的三类配置或配置规则。
- 按客户各自期限评估适配，不把所有客户都按 30 年比较。
- 明确流动性需求的建模方式和人工审核条件。
- 区分保持持仓、恢复原目标、改变目标和人工审核。
- 建立交易相对保持持仓的事前收益与费用判断。
- 比较固定目标、条件再平衡和有限目标更新，识别改进来自哪里。

报告 AI 根据实际规则撰写方法部分。核查 AI 检查规则是否完整、假设是否披露、代码是否实现了声明的决策。

**允许得到“不建议自动更新目标”的结论。** 是否采用复杂策略由开发验证支持，不能为了展示复杂模型而预设答案。

### 阶段四：核查并冻结最终方案

主 AI 在运行最终测试前保存：

- 策略和全部参数；
- 数据划分、指标、费用与交易频率口径；
- 客户适配和人工审核规则；
- 敏感性实验方案；
- 严重情景选择方法；
- 对应代码版本与运行命令。

建议用 `configs/` 中的配置文件和一份冻结记录保存，记录 commit SHA。核查 AI 检查是否仍有足以影响结论的未解决问题。

### 阶段五：最终评估及独立复算

主 AI 使用情景 121–180 评估冻结方案，输出四项规定统计、交易频率、严重案例和预先定义的敏感性实验。

核查 AI 可以复现冻结方案的最终评估，检查汇总与逐情景数据一致。不得利用测试表现提出新的调参以追求更好分数。

若发现实现错误，必须记录错误原因、影响、修复和重跑范围，诚实说明重跑情况。不能把错误修复与根据测试表现更换策略混在一起。

### 阶段六：报告、复核和交付

报告 AI 完成英文报告和必要图表。主 AI 检查报告中的模型与最终代码一致；核查 AI 检查数值、口径、结论和限制。

主负责人整理报告、代码、运行说明和补充 ZIP。队员核对姓名、AI 声明及上传文件，由组长通过 CMT 提交并确认保存。

## 7. 共同遵守的建模边界

### 7.1 费用和时序

```text
上年末持仓及已知历史
  → 本期决策
  → 执行交易并扣费
  → 应用当年各资产收益
  → 更新物价指数及实际财富
```

- 起始 100 单位全部为票据，无后续存取款。
- 只能做多且全额投资。
- 资产间转移金额收费 0.25%，同一转移只计一次；20 单位转移费用为 0.05。
- 初始配置同样收费，不能在当期收益之后才扣费。
- 费用从哪里支付、目标在扣费前还是扣费后成立，需要主 AI 明确并保持账本守恒；不能默认不同实现完全等价。
- 忽略税、其他费用和终值清算费用。

### 7.2 购买力与风险

```text
实际收益率 = (1 + 名义收益率) / (1 + 通胀率) - 1
实际财富 = 名义财富 / 累计物价指数
```

风险需要分别描述普通波动和严重损失。严重损失指标数值越大应表示越差。若选最大回撤，应写明使用的财富采样时点，包括初始财富，并披露年度数据不能识别年内更深跌幅的局限。

候选增长指标为实际年化复合增长率，候选严重损失指标为实际财富最大回撤；这些是目前建议，不替主 AI 提前确定最终模型。

### 7.3 数据边界

- 情景 1–120：开发、内部验证与参数选择。
- 情景 121–180：冻结后的最终评估。
- 第 t 年决策只能使用该情景截至第 t-1 年的已知信息，以及允许使用开发集事先估计并冻结的模型。
- 不将不同情景串成一条长时间序列，不用最终测试数据拟合统计量或选择策略。
- 数据结构检查不等于获得使用测试表现调参的许可。

### 7.4 客户与人工审核

- A–E 分别按 5、15、30、25、6 年评估。
- 损失容忍度不是损失保证，票据不是实际购买力无风险资产。
- 高流动性需求不能被擅自实现为题目禁止的提款；配置限制等做法需明确是建模假设。
- 审核触发用当时已知信息，等待期间的持仓与动作必须可执行并纳入回测。
- 不能默认为人工顾问拥有完美预测能力。

## 8. 核查范围与问题处理

详细项目见[audit/CHECKLIST.md](audit/CHECKLIST.md)。重点是：

| 范围 | 核查重点 |
|---|---|
| 题意覆盖 | 三类组合、五位客户、四类动作、规定统计、保障措施是否齐全 |
| 账本 | 初始费用、单向收费、资金守恒、非负持仓、收益时序 |
| 指标 | 实际购买力、增长、波动、严重损失、分位数计算 |
| 信息边界 | 未来数据、训练测试混用、当年观测提前使用 |
| 策略 | 交易的事前成本收益理由、目标更新和再平衡的区别 |
| 客户 | 各自期限、风险与流动性约束、不能适配时转人工 |
| 实验 | 相同情景公平比较、冻结配置、费率敏感性、严重案例 |
| 报告 | 数值可追溯、结论有支持、引用可核实、格式满足要求 |

核查状态分别记录为“待提供”“待核查”“发现问题”“已修复待复核”“该项通过”。只有存在具体检查证据时才标记通过，并注明版本和范围。

问题记录示例：

```text
编号：AUD-001
所查版本：完整 commit SHA
状态：发现问题
位置：文件与行号
复现：输入和运行命令
期望：独立计算或原题要求
实际：程序输出
影响：哪些实验或结论受到影响
建议：需要修改的具体点
复核：修复后的 SHA、检查证据和结论
```

## 9. 每次交接需要提供什么

只说“完成了”“效果很好”不足以交接。建议将以下信息写入对应目录的交接记录，并在聊天中提供链接。

```text
角色：主 AI / 核查 AI / 报告 AI
本轮任务：
分支与 commit SHA：
新增或修改文件：
运行或复现命令：
完成的检查及结果：
仍未解决的问题：
需要下一位处理的事项：
数据范围：开发 / 冻结后最终评估 / 合成核查样例
```

主 AI 第一轮至少交付：主程序入口、依赖、费用说明、一个开发情景逐期账本、逐情景指标、汇总结果和 SHA。

逐期账本建议包含情景、年度、交易前持仓、动作、转移额、费用、交易后持仓、年末持仓、物价指数及实际财富。具体列名由主 AI 定义，但含义应清楚。

报告中的每个数值应能追溯到实验文件和版本；核查报告也应注明所查版本，不能把旧版本通过结论直接套到新代码。

## 12. 常见疑问

**能让 AI 从头做到代码和报告吗？**

有相应文件、运行和文档工具时，可以承担数据处理、模型实现、实验、核查、图表、报告及打包。具体完成情况以实际运行和交付文件为准，不以计划或口头承诺代替。成员信息及最终提交仍需队员核对。

**为什么先做基准，不直接做复杂模型？**

费用、通胀、时序和指标是全部实验共同的基础。先独立核对这些环节，能减少把基础错误带进多个策略的风险。

**核查 AI 能直接读队友电脑吗？**

不能。队友先上传代码和必要结果，核查 AI 再从 GitHub 获取明确版本。缺少代码时只能核查题意和方案，不能宣称代码通过。

**报告 AI 现在就可以开始吗？**

可以先整理题意、结构、符号、假设和文献。实验结果、推荐和数值结论必须等实际研究完成后填写。

**三个 AI 是否需要每一步都等用户确认？**

常规实现、核查、写作和修复在各自授权范围内自行推进。需要另一个角色处理时，用文件和版本清楚交接；缺少关键材料时明确指出，不能假定对方已经完成。

**方案收益不如基准怎么办？**

如实报告。减少尾部风险、降低交易或拒绝无价值的自动更新，都可能形成合理结论；需要根据题目目标和实验权衡，不能只挑表现好的情景。

**这里是否已经有正式投资建议？**

没有。本项目针对虚构公司及竞赛合成数据。配置示例、适配门槛和候选策略均需研究验证，不能将它们描述为经过回测的结果。
